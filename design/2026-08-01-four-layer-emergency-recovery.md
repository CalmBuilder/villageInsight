# 四层模板完整应急恢复方案

## 目标与边界

`restore-four-layer-baseline.sh` 只恢复四层模板，不恢复或覆盖业务数据。恢复点必须随
Git 交付，单文件严格小于 100,000,000 bytes，不能依赖被 `.gitignore` 排除的
`backups/`，也不能要求使用包含业务数据的完整数据库 dump。

## 完整恢复包

默认恢复点 `current-205-expanded` 对应 205 条目四层闭合报告和已知语料 v8 精确回归，
四层发布对象为 `1075 / 386 / 328 / 210`。恢复包位于：

`recovery/four-layer-baselines/current-205-expanded/catalog-bundle.json.gz`

包内包含以下完整关系数据：

- 字段、字段版本、字段变体和字段审核事件；
- Region 模板、版本和审核事件；
- Sheet 组合、版本、Region 槽位和审核事件；
- 文件路由、版本、Sheet 槽位和审核事件；
- 同一包生成时的发布状态快照、逐表数量及逻辑摘要。

不包含用户、租户、上传文件、批次、解析结果、JSONB 业务记录、问答数据或密钥。
审核事件保留操作者文字和类型；目标库不存在原用户时，只把可空的 `actor_user_id`
置空，不引入用户数据依赖。

## 恢复语义

1. `--list` 离线校验文件 SHA-256、包逻辑摘要、发布快照、四层数量和文件大小。
2. `--dry-run` 在数据库事务中执行完整恢复后回滚，逐表报告 inserted、updated、
   removed_extra 和 unchanged，并报告发布状态变化。
3. 正式恢复先在 `backups/four-layer-pre-restore/` 导出目标库当前完整模板包。
4. 在 PostgreSQL advisory lock 和单一事务中：
   - 补回缺失的基线对象、版本、变体、槽位和审核事件；
   - 修复主键相同但内容被篡改的基线行；
   - 删除挂在基线版本上但不属于基线的行为子项，仅限字段变体和组合槽位；
   - 保留基线之后的模板对象、版本和额外审核事件；
   - 最后切换发布指针和状态，使新增对象停止参与匹配。
5. 任一步失败则整个模板恢复事务回滚，业务表始终不在写入表集合中。

## 验收

- 单元测试覆盖完整包读写、空库恢复、内容篡改修复、额外行为行清理、业务哨兵表不变、
  路径边界、文件摘要和 100MB 门禁。
- 在独立 PostgreSQL 空库迁移到当前 Alembic head 后执行 dry-run 和正式恢复。
- 独立库恢复后必须得到 `1075 / 386 / 328 / 210`，第二次 dry-run 全部 unchanged。
- 对全部非模板表记录恢复前后行数摘要，必须完全一致。
